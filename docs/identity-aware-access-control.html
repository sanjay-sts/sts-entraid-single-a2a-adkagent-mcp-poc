1. Architecture at a glance

Identity propagates from the React frontend through three independent enforcement tiers before reaching any cloud resource. Each tier performs its own authentication and authorization — a token that passes Tier 1 still gets re-evaluated at Tiers 2 and 3.

Three-tier access control

2. Multi-IdP identity — why two providers

The system treats Entra ID and AWS Cognito as first-class peers. Every tier auto-detects the IdP from the iss (issuer) claim — no per-request configuration required.

# dev_config.py:82-94
def detect_provider(claims: dict) -> str:
    iss = claims.get("iss", "")
    if "login.microsoftonline.com" in iss or "sts.windows.net" in iss:
        return "entra"
    if "cognito-idp" in iss:
        return "cognito"
    return "unknown"

Used by: A2A server (group claim extraction), MCP middleware (Cognito client_id re-validation), ADK agent (email claim mapping).

Cognito audience hack: Cognito access tokens do not have an aud claim. Instead they carry client_id. All three tiers skip standard audience validation for Cognito tokens and manually compare token.client_id == COGNITO_CLIENT_ID.

4. ADK Agent — Tier 2 session state & header injection

The ADK agent bridges the A2A gateway to the FastMCP server. It stores user identity in session state with a user: prefix and re-injects auth headers into every MCP tool call.

Session state with user: prefix

# adk_agent/agent.py:216-228
initial_state = {
    "user:access_token": access_token,     # raw JWT — re-sent to MCP
    "user:email":        email,
    "user:name":         name,
    "user:groups":       groups,
    "user:role":         role,              # assumed role (admin/developer/viewer)
    "user:abac_attrs":   json.dumps(abac_attrs),  # serialised to string
}

mcp_header_provider — per-request header injection

This sync callback is invoked by McpToolset before every MCP request. It reads from session state and builds the three headers the MCP server needs.

# adk_agent/agent.py:99-118
def mcp_header_provider(readonly_context: ReadonlyContext) -> dict[str, str]:
    headers = {}
    if readonly_context and readonly_context.state:
        access_token = readonly_context.state.get("user:access_token", "")
        role         = readonly_context.state.get("user:role", "")
        abac_attrs   = readonly_context.state.get("user:abac_attrs", "")
        if access_token: headers["Authorization"]  = f"Bearer {access_token}"
        if role:         headers["X-Assume-Role"]  = role
        if abac_attrs:   headers["X-Abac-Attrs"]   = abac_attrs
    return headers

UserContextMiddleware — two strictness modes

# mcp_server/server.py:317-331
async def on_list_tools(self, context, call_next):
    # Lenient — auto-selects highest available role for UI rendering
    self._resolve_context(raise_on_error=False)

async def on_call_tool(self, context, call_next):
    # Strict — requires X-Assume-Role header; raises ToolError on mismatch

Why ContextVars instead of ctx.get_state()? FastMCP runs in stateless_http=True mode — no server-side sessions. ContextVars survive await boundaries within a single request's async task, giving tool functions safe access to auth data without parameter threading.

6. Cedar — policy management

Cedar is an open-source policy language from AWS. This system uses cedarpy for in-process evaluation — no external PDP network hop, policies reload on file change (mtime check), and evaluation is synchronous inside each MCP tool call.

Schema — entity types and actions

// cedar/schema.cedarschema
namespace AgentAuth {
  entity Role;                          // admin | developer | viewer

  entity User in [Role] {             // User inherits permissions from role
    provider: String,                   // "entra" | "cognito"
    email: String,
    groups: Set<String>,
    department?: String,                // optional ABAC attr
    archiver?: Bool,                    // optional ABAC attr — S3 archive delete
  };

  entity Tool {                         // each MCP tool is a Cedar resource
    sensitivity?: String,               // "public" | "internal" | "confidential"
    requires_provider?: String,         // "entra" | ""
  };

  entity S3Folder;                      // future: path-based sub-resources

  action call_tool appliesTo {
    principal: [User], resource: [Tool],
    context: { resource_path?: String, environment?: String },
  };

  action list_tools appliesTo {         // discovery — no context needed
    principal: [User], resource: [Tool],
  };
}

rbac.cedar — role-based permits

// cedar/policies/rbac.cedar
// Admin: all tools except delete_s3_object (ABAC-only)
permit(
  principal in AgentAuth::Role::"admin",
  action == AgentAuth::Action::"call_tool", resource
) when { resource != AgentAuth::Tool::"delete_s3_object" };

// Developer: 5 specific tools
permit(
  principal in AgentAuth::Role::"developer",
  action == AgentAuth::Action::"call_tool", resource
) when {
  resource == AgentAuth::Tool::"get_user_profile" ||
  resource == AgentAuth::Tool::"list_files"        ||
  resource == AgentAuth::Tool::"list_s3_buckets"   ||
  resource == AgentAuth::Tool::"list_s3_objects"   ||
  resource == AgentAuth::Tool::"get_s3_object_info"
};

// Viewer: 2 read-only tools
permit(
  principal in AgentAuth::Role::"viewer",
  action == AgentAuth::Action::"call_tool", resource
) when {
  resource == AgentAuth::Tool::"get_user_profile" ||
  resource == AgentAuth::Tool::"get_s3_object_info"
};

// All authenticated users can discover tools
permit(principal, action == AgentAuth::Action::"list_tools", resource);

abac.cedar — attribute-based permit

// cedar/policies/abac.cedar
// Any user with archiver=true can delete in archive/ — role is irrelevant.
permit(
  principal,
  action == AgentAuth::Action::"call_tool",
  resource == AgentAuth::Tool::"delete_s3_object"
) when {
  principal has archiver &&
  principal.archiver == true &&
  context has resource_path &&
  context.resource_path like "archive/*"
};

guardrails.cedar — hard safety limits

// cedar/policies/guardrails.cedar
// No one can delete in protected/ — forbid overrides all permits.
forbid(
  principal,
  action == AgentAuth::Action::"call_tool",
  resource == AgentAuth::Tool::"delete_s3_object"
) when {
  context has resource_path &&
  context.resource_path like "protected/*"
};
Cedar's deny-wins semantics: a single forbid overrides any number of permit policies. This makes guardrails unconditional — even an admin with archiver=true cannot delete in protected/.

CedarPolicyEvaluator — key internals

mcp_server/policy.py — Key behaviours:

  • Hot-reload: _load() compares mtime of cedar/policies/*.cedar and cedar/entities.json on every call — file changes take effect within one request.
  • Dynamic user entity: _build_user_entity() constructs the Cedar User with ABAC attrs from ABAC_CLAIM_KEYS = {"department": str, "archiver": bool}. Cognito sends booleans as strings; they are normalized.
  • Batch evaluation: check_access_batch() sends all 11 tool requests to cedarpy in one call — used by the /me endpoint for the frontend permission matrix.
  • Assumed-role enforcement: If the user sends X-Assume-Role: developer, only [developer] is passed as the User's parents — preventing privilege escalation to a higher available role.

7. Tool-level RBAC and ABAC — the two-phase pattern

Phase 1 — RBAC check (auth callable on the decorator)

# mcp_server/server.py:349-376
_ABAC_ONLY_TOOLS: set[str] = {"delete_s3_object"}  # no RBAC role grants access

def require_cedar(tool_name: str):
    def check(ctx: AuthContext) -> bool:
        decision = policy_evaluator.check_access(_build_access_request(tool_name))
        if not decision.allowed:
            if tool_name in _ABAC_ONLY_TOOLS:
                return True   # passthrough — Phase 2 will decide
            raise ToolError(f"[TOOL_DENIAL] Access denied: {decision.reason}")
        return True
    return check

# Applied to every tool:
@mcp.tool(auth=require_cedar("get_user_profile"))
async def get_user_profile() -> dict: ...

@mcp.tool(auth=require_cedar("delete_s3_object"))   # passthrough → Phase 2
async def delete_s3_object(bucket: str, key: str) -> dict: ...

Phase 2 — ABAC check (inside the tool function)

# mcp_server/server.py:379-385
def cedar_check_with_context(tool_name: str, context: dict) -> AccessDecision:
    return policy_evaluator.check_access(_build_access_request(tool_name, context))

# Inside delete_s3_object:
decision = cedar_check_with_context("delete_s3_object", {"resource_path": key})
if not decision.allowed:
    return {"error": "abac_denied", "message": f"[TOOL_DENIAL] {decision.reason}"}

# dev_config.py:64-79 — parse_abac_attrs() — used by all three servers
def parse_abac_attrs(raw: str) -> dict:
    if not raw: return {}
    try:
        attrs = json.loads(raw)
        return attrs if isinstance(attrs, dict) else {}
    except (json.JSONDecodeError, TypeError):
        logger.warning("Invalid ABAC attrs JSON: %.100s", raw)
        return {}
Security note: The X-Abac-Attrs header is client-controlled — the frontend can claim archiver: true without a signed token assertion. This is intentional for this demo. In production, ABAC attributes should come from the IdP token (Entra optional claims / Cognito Pre-Token-Generation Lambda) and the header should be ignored or validated server-side.

9. MCP tools as Cedar resources — what the branch name means

Clarification: The branch name mcp-skills-as-resources-abac-rbac does not mean MCP protocol @mcp.resource() / list_resources() / read_resource(). No such endpoints exist in this codebase. The name means that the agent's skills (MCP tools) are modelled as Cedar Tool resources for authorization policy evaluation — the standard Cedar terminology where a resource is the thing being authorized against.

Each of the 11 MCP tools is a AgentAuth::Tool entity in Cedar with a unique ID matching the tool's Python function name. Authorization asks: "Can principal User::"alice@company.com" perform Action::"call_tool" on Tool::"delete_s3_object"?"

What real MCP resource serving would look like (future)

If the project later added skill definitions as MCP protocol resources (e.g., dynamic agent cards), the same Cedar pattern would apply:

  • Add a Skill entity type to cedar/schema.cedarschema
  • Add a read_resource action
  • Add RBAC/ABAC policies in cedar/policies/
  • Apply auth=require_cedar("skill_name") on each @mcp.resource() decorator
  • The S3Folder entity type already in the schema is a placeholder for exactly this kind of sub-resource extension

11. Production considerations

AreaCurrent (demo)Production recommendation
ABAC attributes Client-controlled X-Abac-Attrs header — frontend can claim any attribute Source from signed IdP token: Entra optional claims or Cognito Pre-Token-Generation Lambda. Reject or ignore client-provided overrides.
JWKS cache (A2A) In-memory dict, never time-invalidated, only cleared on key-not-found Add TTL (e.g., 1 hour) and a background refresh to handle keys added before expiry.
Session store (ADK) InMemorySessionService — lost on restart Replace with Redis or DynamoDB-backed session service for multi-instance deployment.
Cedar decision cache Evaluated per request — stateless is safe but adds latency For hot-path tools, cache AccessDecision keyed by (email, role, tool, abac_hash) with a short TTL (30s).
Group overage (Entra) Logged, groups returned as [] Implement GET /me/memberOf via Graph API when _claim_names.groups appears. Requires OBO token with GroupMember.Read.All.
Rate limiting No rate limiting at any tier Add per-user rate limits at A2A gateway. ADK already retries 3× on Bedrock throttles.
S3 delete simulation delete_resource is simulated (logs only) Wire to real IAM-scoped role; add pre-deletion audit log write.
Token refresh Token stored in ADK session at creation; may expire mid-session Check exp claim in mcp_header_provider; trigger silent refresh before forwarding.
