3. Cedar Authorization — How It Works

Cedar is an open-source policy language by AWS. Policies are evaluated in-process via cedarpy.

Cedar rule: permit grants access. forbid denies access and always overrides permit. If no permit matches, access is denied by default.

The Cedar Directory

cedar/
├── schema.cedarschema     # Entity type definitions
├── entities.json          # Static entity instances (3 roles + 10 tools)
└── policies/
    ├── rbac.cedar         # Role-based permits
    ├── abac.cedar         # Attribute-based permits
    └── guardrails.cedar   # Forbid guardrails

3.1 Schema (cedar/schema.cedarschema)

namespace AgentAuth {

  // Principals
  entity Role;
  entity User in [Role] {
    provider: String,           // "entra", "cognito"
    email: String,
    groups: Set<String>,       // IdP group IDs from token
    department?: String,       // Optional ABAC attribute
    archiver?: Bool,           // Optional ABAC attribute
  };

  // Resources
  entity Tool {
    sensitivity?: String,      // "public", "internal", "confidential"
    requires_provider?: String, // "entra" for Graph tools, "" for any
  };
  entity S3Folder;              // Future use

  // Actions
  action call_tool appliesTo {
    principal: [User],
    resource: [Tool],
    context: { resource_path?: String, environment?: String },
  };
  action list_tools appliesTo { ... };
}
Key design: User in [Role] enables role hierarchy. A user with parents: [Role::"developer"] satisfies principal in AgentAuth::Role::"developer" in policies.

3.3 RBAC Policies (cedar/policies/rbac.cedar) RBAC

// Admin: all tools EXCEPT delete_s3_object
permit(
  principal in AgentAuth::Role::"admin",
  action == AgentAuth::Action::"call_tool",
  resource
) when {
  resource != AgentAuth::Tool::"delete_s3_object"
};

// Developer: 5 specific tools
permit( principal in AgentAuth::Role::"developer", ... )
when { resource == ..."get_user_profile" || ..."list_files" || ... };

// Viewer: 2 tools
permit( principal in AgentAuth::Role::"viewer", ... )
when { resource == ..."get_user_profile" || ..."get_s3_object_info" };

// All users can discover tools
permit(principal, action == AgentAuth::Action::"list_tools", resource);
Note: delete_s3_object is deliberately excluded from ALL RBAC permits. Access is granted solely via the ABAC policy.

3.4 ABAC Policy (cedar/policies/abac.cedar) ABAC

permit(
  principal,
  action == AgentAuth::Action::"call_tool",
  resource == AgentAuth::Tool::"delete_s3_object"
) when {
  principal has archiver &&
  principal.archiver == true &&
  context has resource_path &&
  context.resource_path like "archive/*"
};
  • Role is irrelevant — admin, developer, viewer all need archiver=true
  • Path-restricted — only archive/* prefix allowed
  • Attribute source — archiver comes from JWT custom claims or X-Abac-Attrs header

3.5 Guardrail Policy (cedar/policies/guardrails.cedar) FORBID

forbid(
  principal,
  action == AgentAuth::Action::"call_tool",
  resource == AgentAuth::Tool::"delete_s3_object"
) when {
  context has resource_path &&
  context.resource_path like "protected/*"
};
Forbid always wins. Even a user with archiver=true cannot delete in protected/. No exceptions. This is Cedar's enforcement guarantee.

4. Two-Phase Authorization Pattern

This is the core authorization design. Tool access is checked in two phases:

Phase 1: RBAC Check (Decorator Level) RBAC

require_cedar() — server.py:355-376

def require_cedar(tool_name: str):
    def check(ctx: AuthContext) -> bool:
        decision = policy_evaluator.check_access(_build_access_request(tool_name))
        if not decision.allowed:
            if tool_name in _ABAC_ONLY_TOOLS:   # {"delete_s3_object"}
                return True                       # Pass through to Phase 2
            raise ToolError(f"[TOOL_DENIAL] Access denied: {decision.reason}")
        return True
    return check

Phase 2: ABAC Check (Inside Tool) ABAC

cedar_check_with_context() — server.py:379-385

# Inside delete_s3_object (server.py:721-723):
decision = cedar_check_with_context("delete_s3_object", {"resource_path": key})
if not decision.allowed:
    return {"error": "abac_denied", "message": f"[TOOL_DENIAL] {decision.reason}"}

Why Two Phases?

ScenarioPhase 1Phase 2Result
Developer calls list_files RBAC permit matches N/A ALLOWED
Viewer calls send_email RBAC denies N/A DENIED
Developer (archiver=true) calls delete_s3_object key=archive/old.txt No RBAC permit → PASSTHROUGH (ABAC-only) archiver + archive/* → permit ALLOWED
Admin (archiver=true) calls delete_s3_object key=protected/secret.txt PASSTHROUGH Guardrail forbid: protected/* DENIED

How check_access() Works

policy.py:265-326

  1. Hot-reload — Check file mtimes, reload policies/entities if changed
  2. Resolve roles — TomlPolicyEvaluator.get_available_roles() maps groups → roles
  3. Enforce assumed role — If user selected a role, restrict parents to only that role
  4. Build dynamic User entity — Email, provider, groups, ABAC attrs, role parents
  5. Merge entities — Static (roles + tools) + dynamic (user)
  6. Build Cedar request — Principal, action, resource, context
  7. Evaluate — cedarpy.is_authorized() returns decision

6. Permissions File — Role Resolution

Template: permissions.example.toml → copy to permissions.toml (gitignored)

Used by: TomlPolicyEvaluator (composed inside CedarPolicyEvaluator)

# PRIMARY: Group-to-role mapping (per Identity Provider)
[group_rules.entra]
"72460602-..." = "admin"       # Entra group GUID → role
"4baa4106-..." = "developer"

[group_rules.cognito]
"platform-admins" = "admin"    # Cognito group name → role
"platform-developers" = "developer"
"platform-viewers" = "viewer"

# OPTIONAL: Direct user overrides
[users]
# "sanjay@company.com" = { role = "admin" }

# FALLBACK: Default for unmatched users
[defaults]
unknown_users = "none"         # "none" = no access

Resolution Logic

1. GROUP MAPPING (primary): For each group in token claims → look up in group_rules[provider] → add role 2. USER OVERRIDE (secondary): Look up email (case-insensitive) in [users] → add role 3. DEFAULT (tertiary): If no roles matched → use defaults.unknown_users If "none" → return [] (no access) 4. SORT by priority: admin > developer > viewer Return: ["admin", "developer"] (highest first)

How Roles Become Cedar Entities

permissions.toml: "platform-admins" = "admin" ↓ TomlPolicyEvaluator: roles = ["admin"] ↓ _build_user_entity: parents = [{type: "AgentAuth::Role", id: "admin"}] ↓ Cedar: principal in AgentAuth::Role::"admin" → TRUE
ABAC attributes (archiver, department) come from JWT custom claims, not from permissions.toml. Configure in Entra ID (Optional Claims) or Cognito (Pre Token Generation Lambda).

8. Graph OBO Token Exchange

File: mcp_server/graph_obo.py (114 lines)

What It Does

OBO (On-Behalf-Of) exchanges the user's custom-audience JWT (api://{CLIENT_ID}) for a Microsoft Graph-scoped token. This allows MCP tools to call Graph API as the user, not as the application.

Architecture

User's JWT (audience: api://CLIENT_ID) │ ▼ GraphOBOExchanger.get_graph_token() │ ├── Get/create OnBehalfOfCredential (cached by assertion hash) ├── credential.get_token("https://graph.microsoft.com/.default") │ ▼ Graph-scoped token (audience: https://graph.microsoft.com) │ ▼ Graph API call (GET /me, GET /me/drive, POST /me/sendMail)

Key Implementation Details

AspectDetail
PatternModule-level singleton via init_obo_exchanger() + get_obo_exchanger()
CacheLRU dictionary of OnBehalfOfCredential, keyed by SHA-256 of user assertion, max 128 entries
Azure SDKazure.identity.aio.OnBehalfOfCredential (async)
Required EnvENTRA_TENANT_ID, ENTRA_CLIENT_ID, ENTRA_CLIENT_SECRET
ScopeEntra-only — Cognito/Auth0 users cannot exchange tokens for Graph

Token Fallback Chain

# Priority:
1. OBO-exchanged Graph token   # If ENTRA_CLIENT_SECRET set + Entra user
